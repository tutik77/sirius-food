# ЛР № 8. Ответы на контрольные вопросы

**1. Чем Server Component отличается от Client Component? Приведите пример из работы.**
Server Component выполняется только на сервере Next.js: может быть `async`, ходить в API и БД напрямую,
его код не попадает в браузер. Client Component (директива `"use client"`) выполняется в браузере, в нём доступны
`useState`, `useEffect` и обработчики событий, но он не может быть `async`. В работе: `menu/page.tsx` и
`menu/[id]/page.tsx` — серверные, получают меню через `await getMenuItems()`; `AddToCartButton`, `error.tsx`
и `/menu-csr` — клиентские (состояние кнопки, `reset`, `useEffect`). Серверный компонент может рендерить
клиентский, но не наоборот.

**2. Почему для витрины выбран SSR, а не чистый CSR?**
Витрина публичная: важны скорость первого показа и SEO. При SSR браузер сразу получает HTML с блюдами,
а поисковик и мессенджеры видят готовое содержимое. При CSR приходит пустой каркас, блюда появляются только
после загрузки JS и запроса к API — в замерах в 4–6 раз позже. Личный кабинет, наоборот, можно делать CSR:
он за авторизацией и интерактивный.

**3. Как проверить, что данные отрендерены на сервере?**
Открыть исходный код страницы (Ctrl+U) или `curl -s http://localhost:3000/menu | grep Сырники` — при SSR названия
блюд есть в HTML. Второй признак — во вкладке Network браузера нет запроса к `:8000/menu/items`: запрос сделал
сервер Next.js. У `/menu-csr` блюд в HTML нет, а в Network виден запрос к API.

**4. Зачем нужен loading.tsx и error.tsx? Что будет, если их нет?**
`loading.tsx` автоматически оборачивает страницу в Suspense: пока сервер ждёт данные, пользователь видит
скелетон, а не пустоту. `error.tsx` — граница ошибок: если API недоступен и `getMenuItems()` бросил исключение,
показывается понятное сообщение и кнопка «Попробовать снова» (`reset` перерисовывает сегмент). Без них
пользователь при медленном API смотрит на белый экран, а при ошибке получает общую страницу ошибки Next.js.

**5. Почему в Next.js 16 params — это Promise? Что будет, если забыть await?**
Next.js рендерит страницы потоково и может начать работу до того, как параметры маршрута вычислены, поэтому
`params` асинхронны. Если не написать `const { id } = await params`, обращение `params.id` вернёт `undefined`
(у Promise нет поля `id`), запрос уйдёт на `/menu/items/undefined`, и `getMenuItem` вернёт `null` → 404.

**6. Чем кеш Next.js отличается от кеша Redis?**
Redis (ЛР № 4) кеширует данные на бэкенде: список блюд, чтобы не ходить в PostgreSQL. Next.js кеширует результат
`fetch` и готовый HTML страницы (ISR, `revalidate = 60`): 60 секунд страница отдаётся без рендеринга и без
запроса к бэкенду, потом пересобирается в фоне. Есть ещё третий уровень — кеш браузера (HTTP-заголовки).
Это разные уровни: изменение цены сбрасывает Redis-кеш сразу, а витрина обновится не позже чем через 60 с.

**7. Зачем нужны метатеги Open Graph? Где их видно, кроме вкладки браузера?**
`og:title`, `og:description`, `og:type`, `og:url` описывают страницу для внешних сервисов: по ним Telegram,
VK, WhatsApp, Slack строят карточку-превью ссылки, а поисковики — сниппет в выдаче. Без них превью будет пустым
или со случайным текстом. У нас `generateMetadata` формирует их для каждого блюда из данных API.

**8. Что такое BFF и зачем он нужен?**
Backend for Frontend — слой на бэкенде под конкретного клиента, который отдаёт ему данные в удобной форме
одним запросом и скрывает внутреннюю архитектуру (из какого сервиса что пришло). Мы выбрали вариант А
(SEO + ISR), BFF не реализовывали: фронтенд ходит в REST `/menu/items` монолита.
