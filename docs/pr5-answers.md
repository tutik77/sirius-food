# ЛР № 5. Ответы на контрольные вопросы

**1. Почему вызов фоновых задач реализован в слое Service, а не в Router? Как это связано с Clean Architecture?**
«После оформления заказа сформировать чек и уведомить клиента» — бизнес-правило сценария оформления.
Если ставить задачи в роутере, правило будет работать только для HTTP: заказ, созданный из CLI или
другого сервиса, останется без чека. Сервис — единственное место, где живёт сценарий, поэтому он и ставит
задачи (`OrderService._schedule_order_notifications`). Роутер только принимает запрос, репозиторий только хранит.
Сервис по-прежнему не импортирует FastAPI, SQLAlchemy и Redis.

**2. Что произойдёт, если Celery-воркер отключится во время выполнения задачи?**
Пока воркер выключен, новые задачи копятся в брокере (Redis-список `default`) и не теряются: API продолжает
отвечать быстро, а задачи выполнятся, когда воркер поднимется. Задача, которую воркер выполнял в момент
падения, по умолчанию уже подтверждена (ack при получении) и может потеряться. Чтобы её не терять,
включают `acks_late=True`: подтверждение после выполнения, тогда задача вернётся в очередь и выполнится
повторно. Повтор безопасен только при идемпотентности задачи.

**3. Что такое идемпотентность и почему она важна для фоновых задач?**
Идемпотентная операция при повторном выполнении даёт тот же результат, что и при однократном.
Celery гарантирует доставку «как минимум один раз»: задача может выполниться повторно после ретрая,
падения воркера или ручного перезапуска из DLQ. Без идемпотентности клиент получит два письма и два чека.
В проекте задача проверяет ключ `pdf_generated:{order_id}` (`email_sent`, `sms_sent`) в Redis и пропускает
работу, если он есть. Ключ ставится только после успешного выполнения.

**4. Зачем нужны ретраи с экспоненциальной задержкой?**
Внешний сервис (почта, SMS-шлюз) часто недоступен временно: перегрузка, сетевой сбой. Мгновенный повтор
обычно падает снова и добивает перегруженный сервис. Экспоненциальная задержка (1, 2, 4 с, …) даёт ему время
восстановиться и уменьшает нагрузку от повторов. `max_retries=3` ограничивает число попыток, `retry_backoff_max`
ограничивает задержку сверху. Jitter (случайный разброс задержки) нужен при массовых сбоях, чтобы тысячи задач
не повторялись в одну и ту же секунду; в проекте он выключен, чтобы на демонстрации были видны ровно 1, 2, 4 с.

**5. Что такое Dead Letter Queue и как её использовать?**
Очередь для сообщений, которые не удалось обработать после всех попыток. Задача не теряется и не крутится
бесконечно в основной очереди. В проекте `ReliableTask.on_failure` кладёт задачу с теми же аргументами
в очередь `dlq`, а воркер слушает только `default`. Разбор: посмотреть содержимое (`redis-cli lrange dlq 0 -1`
или Flower → Broker), устранить причину (починить почтовый сервис, исправить данные) и перезапустить задачи
воркером на очереди `dlq`: `celery -A app.core.celery_app worker -Q dlq`. На размер DLQ ставят алерт.

**6. Почему Celery — стандарт индустрии, а не просто threading или asyncio?**
Потоки и asyncio-задачи живут внутри процесса API: при перезапуске или падении процесса задачи теряются,
тяжёлая работа отнимает ресурсы у обработки запросов, а масштабировать её можно только вместе с API.
Celery хранит задачи в брокере вне процесса, выполняет их в отдельных воркерах, которые масштабируются
независимо, и из коробки даёт ретраи, расписание (Beat), очереди с приоритетами и маршрутизацией,
результаты задач и мониторинг (Flower).

**7. Чем Celery Beat отличается от обычной задачи?**
Обычная задача ставится в очередь кодом приложения в ответ на событие (создан заказ). Beat — отдельный
процесс-планировщик: по расписанию (`beat_schedule`) он сам ставит задачи в очередь, как cron.
Выполняет их тот же воркер. Beat должен быть запущен в одном экземпляре, иначе задача будет ставиться
несколько раз. В проекте Beat раз в минуту ставит `update_daily_order_stats`.
