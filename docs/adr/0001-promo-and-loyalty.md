# ADR 0001. Промокоды и лояльность: атомарность, идемпотентность, Saga

Статус: принято. Трек A учебной практики.

## Контекст

Промокод с лимитом использований и баллы лояльности — деньги. Нужно, чтобы:
- промокод с `max_uses=1` при одновременных заказах применился ровно один раз;
- баллы не начислились и не вернулись дважды при повторной доставке событий (RabbitMQ — at-least-once);
- отмена заказа вернула баллы и восстановила промокод, хотя это разные модули.

## Решения

**1. Резерв промокода — атомарный условный UPDATE, а не `SELECT … FOR UPDATE`.**
`UPDATE promo_codes SET current_uses = current_uses + 1 WHERE id = :id AND current_uses < max_uses`
(`SqlAlchemyPromoRepository.reserve_use`). Проверка и увеличение — одна операция в БД: второй конкурентный запрос
ждёт блокировку строки, после коммита первого видит `current_uses = 1` и обновляет 0 строк → `PromoCodeExhaustedError`.
Резерв, заказ, запись `promo_code_usages` и списание денег — одна транзакция (одна сессия на запрос), поэтому при
любой ошибке откатывается всё. `FOR UPDATE` тоже корректен, но требует двух запросов и держит блокировку дольше.
Проверено тестом `tests/integration/test_promo_race.py`: 30 параллельных заказов на PostgreSQL → ровно 1 применение.

Правило «клиент применяет код один раз» держит уникальный индекс `(promo_code_id, user_id)` в `promo_code_usages`:
проверка в сервисе даёт понятную ошибку в обычном случае, а при параллельных заказах одного клиента второй
INSERT получает нарушение уникальности → `PromoCodeAlreadyUsedError`, транзакция с резервом откатывается.
Промокоды по условию разовые, поэтому правило действует для всех кодов (отдельного флага нет).

**2. Идемпотентность — уникальные ключи в БД.**
`loyalty_transactions.idempotency_key` уникален: `earn_order_{id}`, `spend_order_{id}`, `refund_order_{id}`,
`revoke_earn_order_{id}`. Перед операцией сервис ищет транзакцию с ключом; уникальный индекс — последняя линия защиты
от гонки. Для промокода ключ компенсации `restore_promo_order_{id}` фиксируется в `processed_events` вместе с
удалением `promo_code_usages`.

**3. Отмена — Saga (хореография) через события, а не прямые вызовы.**
Заказы публикуют `order.cancelled` (через outbox из ЛР № 7); лояльность и промокоды подписаны своими очередями
(`loyalty_queue`, `promo_queue`) и компенсируют свою часть независимо. Заказы не знают о лояльности и промокодах.

**4. Деньги — `Numeric(12, 2)` и `Decimal`.**
В новых таблицах суммы хранятся в `Numeric`, в коде — `Decimal` с округлением до копейки (`money()`); старое поле
`orders.total_cost` осталось `Float` из MVP, на границе значения переводятся в `Decimal`.

**5. Срок действия — обе стратегии.**
Ленивая проверка при применении (`PromoCode.is_valid_at`) гарантирует корректность в любой момент, Celery Beat раз
в час (`deactivate_expired_promo_codes`) проставляет `is_active = false`, чтобы в админке было видно реальное состояние.

## Последствия

- Корректность при гонках и повторах обеспечивает БД, а не код приложения.
- Начисление баллов отстаёт от оплаты на время доставки события (согласованность в конечном счёте).
- Отзыв начисленных баллов не уводит баланс в минус: если баллы уже потрачены, отзывается остаток.
